# Rancor

Rerunnable eval + static leaderboard scoring LLMs on hate/bias. v1.0 ships one
axis, Islamophobia; antisemitism was cut before release, items and all. Axes
are data packs, not code. Monorepo: `eval/` (Python pipeline, package
`rancor`) and `site/` (Astro static leaderboard).

## Which file owns what

Three instruction files, deliberately non-overlapping. Put a fact in exactly
one and link to it from the others; duplicated guidance drifts and then
contradicts itself.

- **CLAUDE.md** (this file) — the rules that must not be broken, and the stack
  that must not be substituted. Rule numbers are cited from source comments
  (`hard rule 4` in `manifest.py`, `export.py`, `judge.py`, `run.py`), so they
  are stable identifiers: append, never renumber.
- **AGENTS.md** — how to actually work here: commands, module map, and the
  gotchas that cost time (root `.venv`, two API keys, per-judge
  `reasoning_effort`, scope flags that turn a $10 run into a $43 one).
- **SPEC.md** — what the product is: data model, rubrics, metrics, the site's
  surfaces, and the core user journeys. Section numbers are cited from source
  the same way. It is authoritative for scoring; see rule 6.

## Commands

Run from the repo root. The virtualenv is `.venv` at the **root**, not inside
`eval/` — `rancor.envfile.load_dotenv()` resolves `.env` relative to the
working directory, so commands run from `eval/` silently see no keys.

- `make test` — pytest (`cd eval && ../.venv/bin/pytest`)
- `make lint` — ruff
- `make validate` — prompt-set validator
- `make e2e-dry` — whole pipeline, zero API calls, from a clean checkout
- `cd site && npm run dev` / `npm run build` / `npm test`
- `./.venv/bin/python -m rancor.run --dry-run` — eval with fixture responses

Regenerating published data:
- `./.venv/bin/python -m rancor.export runs/<id>` — rewrites `site/src/data/`
- `python3 scripts/archive_reports.py` — rewrites `site/src/data/reports/`
  from the runs listed in `reports.yaml`

## Stack (pinned; do not substitute without asking)

- Python 3.11+, LiteLLM for all model calls, PyYAML, SQLite (stdlib), pandas
- Astro + plain CSS on the site; no React, no runtime JS beyond what the
  transcript browser needs; site reads only static JSON from `site/src/data/`
- GitHub Actions for rerun workflow

## Hard rules

1. NEVER fabricate data: no invented model responses, scores, statistics,
   citations, or example transcripts. Demo/fixture data must be clearly
   labeled `fixture` and generated by the dry-run path, never hand-written
   to look like real model output.
2. NEVER commit secrets. API keys come from env vars via `.env`
   (gitignored); `.env.example` documents required vars. Never hardcode keys.
3. The prompt set is versioned data: `prompts/v1.0/` is append-only during
   development and FROZEN (hash recorded) at release. Every scored item
   carries `axis`, `source`, and `rationale` fields; items adapted from BBQ
   or HateCheck carry their upstream ID and CC-BY-4.0 attribution.
4. Every full run writes a run manifest (model snapshot IDs, timestamp,
   decoding params, judge versions, prompt-set SHA-256, git commit) before
   any scores are reported.
5. Refusals are data, not errors: log and score them per the category
   rubric in SPEC.md; never retry a refusal into compliance.
6. If a rubric, formula, or category rule in SPEC.md seems ambiguous,
   ask; do not improvise scoring logic.
7. Axes are symmetric: every category, rubric structure, metric, and
   validator applies identically to every axis. Never special-case one
   axis in code. Never compute or display a cross-axis composite except
   via the matched-trope parity view defined in SPEC.md section 6.
8. Two runs may only be compared by subtraction if the instrument held
   still. A difference in prompt-set hash or judge panel means a change in
   scores measures the instrument, not the model, and no delta may be shown
   for that pair — state why instead. See SPEC.md section 11.

## Style

- Type hints everywhere in Python; dataclasses or pydantic for records
- Every metric function gets a unit test with a hand-computable example
- Keep modules small: runner, judging, scoring, export are separate
- Generated data is never hand-edited. `site/src/data/` regenerates from a
  run and `eval/tests/test_published_run.py` compares it byte-for-byte; the
  fix for a wrong number is always to fix its generator and re-run it.
- Never weaken a failing check to make it pass. Two build checks once stayed
  green over a visibly broken page; both were tightened, not relaxed.
